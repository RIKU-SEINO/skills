# 図のスタイル

構成図もシーケンス図も、同じ見た目の文法で描く。読み手が図の種類を問わず「色付きの枠＝グループ、白い箱＝実体、赤＝問題、灰＝補助」と読めるようにするため。

見本: `examples/architecture.mmd`（構成図）、`examples/sequence.mmd`（シーケンス図）

## 共通

### 図は 1 つの結論に答える

壁打ちで決めた「この図で伝えたい結論」が一目で読めるように描く。結論に効く違いだけを色で強調し、それ以外は控えめにする。伝えたいことが 2 つ以上あるとき、箱が 30 を超えそうなときは図を分ける（as-is / to-be、全体 / 詳細）。

### 粒度

- 箱 1 つは、役割を持つ実体 1 つ（Pod、サービス、DB、外部 API）
- 同じ種類のものは同じ名前で並べ、違いは所属先や属性で見せる
- 比べる対象は全部並べる。関係しないものも省かず「→ なし」のように書いて残す。全体のうちどれに起きるかが結論になることが多いため

### 名前と文

- 日本語で書く。箱の名前は「種類（具体名）」: `ノード（batch-node-1）`、`PostgreSQL（orders）`
- 結論に効く属性は名前に入れる: `ノードの SG（db-access なし）`、`DB（受け付ける接続元：db-access）`
- 矢印の文は「何をする → 対象・結果」の短文: `ジョブをポーリング → payments の集計`
- 失敗する矢印は理由を括弧で添える: `接続して集計する（SG で弾かれる）`
- 名前や文に `|` と `"` を入れない（Mermaid の構文と衝突してパースエラーになる）

### 色の意味

意味を持たせた色は、その意味以外に使わない。

| 意味 | 塗り | 線 |
|---|---|---|
| 問題・失敗 | `#fde2e2` / `rgb(253,226,226)` | `#d33` |
| 成功（失敗と対比するとき） | `#F0FDF4` / `rgb(240,253,244)` | `#16A34A` |
| 補助の流れ（ポーリング、応答、前提の通信） | — | `#999` |
| 位置や存在が決まっていないもの・候補 | `#f5f5f5`（文字 `#555`） | `#888` の点線 |

### 強調のしかた

結論が何の違いかによって、強調の道具を選ぶ。

- **成功と失敗の対比**: 失敗を赤、成功を緑にする
- **主役と脇役の対比**（主系と副系、本番と検証、新旧の並走）: 主役の経路を黒の太線（`stroke:#28253D,stroke-width:2px`）、脇役の経路を灰色の点線にする。補助の流れ（灰色の実線）と区別するため、脇役は点線にする
- **対比がない**: 本題の矢印は既定の黒のままにし、補助だけ灰色にする

結論に関わる矢印は、補助の灰色にしない。灰色は「読み飛ばしてよい」という合図になるため。

### グループの配色

グループ（構成図の subgraph、シーケンス図の box）には redux-color テーマの配色を使う。入れ子や隣り合うグループは別の色にする。赤系の 2 色（`#FEF2F2`、`#FFF1F2`）は「問題」と紛れるので使わない。

| 塗り（hex） | 塗り（rgb） | 線 |
|---|---|---|
| `#FDF4FF` | `rgb(253,244,255)` | `#E879F9` |
| `#F0FDFA` | `rgb(240,253,250)` | `#2DD4BF` |
| `#FFF7ED` | `rgb(255,247,237)` | `#FB923C` |
| `#ECFEFF` | `rgb(236,254,255)` | `#22D3EE` |
| `#F0FDF4` | `rgb(240,253,244)` | `#4ADE80` |
| `#F5F3FF` | `rgb(245,243,255)` | `#A78BFA` |
| `#FEFCE8` | `rgb(254,252,232)` | `#FACC15` |
| `#EEF2FF` | `rgb(238,242,255)` | `#818CF8` |
| `#F7FEE7` | `rgb(247,254,231)` | `#A3E635` |
| `#F0F9FF` | `rgb(240,249,255)` | `#38BDF8` |

### 置き方

左から右へ。左に内側（クラスタ、自サービス）、右に外側（DB、外部サービス）を置く。

## 構成図（flowchart）

```
flowchart LR
  subgraph K8S["Kubernetes クラスタ（demo-cluster）"]
    subgraph N1["ノード（app-node-1）"]
      W1["ジョブ Worker Pod"]
    end
  end
  subgraph DBS["DB（受け付ける接続元：db-access）"]
    DBP[("PostgreSQL（payments）")]
  end
```

- 境界（クラスタ、ノード、SG、VPC、アカウント）は subgraph の入れ子で表す。所属が結論に効くことが多いので省かない
- ID は短い英数字（`W1`、`SCH1`、`DBO`）。名前は必ず `["..."]` で囲む（括弧や記号を含むため）
- DB は円柱 `[("...")]`
- subgraph ごとに配色表から色を付ける: `style N1 fill:#F0FDFA,stroke:#2DD4BF`。問題のある枠は `style S5 fill:#fde2e2,stroke:#d33`
- 位置が決まっていないものは点線の箱にする:
  ```
  classDef movable fill:#f5f5f5,stroke:#888,stroke-dasharray:5 5,color:#555
  class SCH2,SCH3 movable
  ```
- 矢印は補助の流れをまとめて先に書き、本題の流れを後に書く。`linkStyle` の番号は矢印を書いた順（0 始まり）なので、この順にしておくと番号を指定しやすい:
  ```
  linkStyle 0,1,2,3,4,5 stroke:#999
  linkStyle 6,8 stroke:#16A34A,stroke-width:2px
  linkStyle 7 stroke:#d33,stroke-width:2px
  ```
- 成功の緑は、失敗と対比するときだけ使う。対比がなければ本題の矢印は既定の黒のままでよい
- 脇役の経路は点線の矢印 `-.->` で書き、`linkStyle` で灰色にする
- 行きと帰りがある経路（クライアント → ALB → API → ALB → クライアント）は、両向きの矢印 `<-->` 1 本にまとめる。行きと帰りを別々に書くと矢印が輪になり、ELK の並びが崩れて左から右に流れなくなる
- subgraph の中に `direction TB` を書いても、その subgraph の外とつながる矢印があると ELK では効かない。並びを変えたいときは、要素や矢印を書く順番を変える

## シーケンス図（sequenceDiagram）

- グループは `box rgb(...) 名前` 〜 `end` で囲み、配色表の rgb を使う。`box #ECFEFF` のような hex は効かない
- 登場人物は `participant ID as 種類（具体名）`。DB は `participant ID@{ "type": "database", "alias": "PostgreSQL（orders）" }`
- 登場人物の箱は白に黒枠になる（render.py が `themeCSS` を足す）。構成図の白い箱と揃えるため、個別に色は付けない
- 矢印:
  - 本題の要求: `->>`（実線）
  - 補助の流れ・応答: `-->>`（点線。灰色になる）
  - 失敗: `-x`。文の末尾に（理由）
- 結論に関わる応答は、点線ではなく実線 `->>` で書く。点線は灰色になり、読み飛ばされやすいため
- 失敗の区間は `rect rgb(253,226,226)` 〜 `end` で囲む。成功と対比するときは成功の区間を `rect rgb(240,253,244)` で囲む
- 成否以外で区間を分けるとき（同期と非同期、フェーズ 1 と 2）は、配色表の rgb で囲む。box と同じ色、赤と緑は使わない。区間の意味は先頭の `Note` に書く
- `Note` は補足に使う（黄色で出る）。結論そのものは矢印の文と rect で表す
- `autonumber` は、本文から「手順 3 で」のように参照したいときだけ付ける
