# 図を描く

## これが解く問題

説明に図が要るたびに、Mermaid を書き、描画できる場所を探し、見た目を整えるのは手間がかかる。しかも図には構成情報が入ることが多く、mermaid.live のような外部サービスには貼りたくない。

このスキルは「図の中身を詰める → 決まった見た目で描く → 画像を見て直す → 保存する」を一続きにする。図の価値は、1 つの問いに一目で答えていることで決まる。だから描く前に中身を詰め、描いた後は自分で画像を見て確かめる。

## 保存場所

```
~/dev/diagrams/<テーマ>/<図の名前>.mmd
~/dev/diagrams/<テーマ>/<図の名前>.png
```

- テーマと図の名前は英小文字のケバブケース。意味のある名前にする（`batch-db-access/as-is`、`login-flow/before`）。`-2` のような連番は、どの図か分からなくなるので使わない
- 目的と読み手は `.mmd` の中にコメントで持つ。frontmatter（`---` で囲んだ設定）は必ずファイルの 1 行目から始まる必要があるので、コメントはその後ろ、図の種類の行の前に置く:
  ```
  ---
  config:
    theme: redux-color
    layout: elk
  ---
  %% 目的: ...
  %% 読み手: ...
  flowchart LR
  ```

## 1. 何をするか決める

まず「新しく描く」か「保存した図を見る・直す・消す」かを決める。

引数や直前の会話から明らかなら、聞かずに進む。

- 描きたい図の内容が書いてある、Mermaid コードやファイルのパスが渡された → 新規作成
- 保存した図の名前や「さっきの図」を指して、変えたい点が書いてある → 更新
- 「一覧」「どんな図があったっけ」 → 参照
- 「消して」 → 削除

明らかでないときは AskUserQuestion で選んでもらう（「新しく描く」「保存した図を見る・直す・消す」）。`~/dev/diagrams` に図が 1 つもなければ、聞かずに新規作成に進む。

## 2. 新規作成: 図の中身を詰める

次の 5 つが埋まっていれば、そのまま描画に進む。1 つでも欠けていれば壁打ちで埋める。

1. **結論**: この図で伝えたいことを 1 文で
2. **読み手**: 誰が見るか（チーム内、SRE、他チーム、PdM）。前提知識と、どこまで細かく描くかが決まる
3. **要素と所属**: 登場する実体と、どの境界（クラスタ、ノード、VPC、サービス）に入るか
4. **流れ**: 誰から誰へ、何をするか
5. **強調する違い**: 成功と失敗、変更前と変更後など、色で見せる差

壁打ちは 1 問ずつ聞く。推測できるところは「〜でいいか」と案を出して確かめる。まとめて聞くと答える側の負担が大きく、答えも浅くなるため。

図の種類もここで決める。「どこに何があり、何が届く・届かない」なら構成図、「どの順で何が起きる」ならシーケンス図。両方要るなら 2 枚に分ける。

図に書くのは、会話やユーザーの説明で確定した事実だけにする。リポジトリや外部のサービスを調べて事実を足すことはしない。調べた結果がユーザーの意図と合っているかは分からず、もっともらしい図は、間違っていても正しく見えてしまうため。分からないところの扱いは、結論に効くかどうかで分ける。

- 結論に効くところ（強調する経路の向き、問題の起きる場所）が分からない → 描く前に聞く
- 結論に効かない細部（脇にある要素の置き場所など）が分からない → 仮に置いて描き、報告で「仮に置いた点」として確認する

Mermaid コードやファイルを渡されたときは、壁打ちを飛ばす。保存先のテーマと名前だけ決めて描画に進む。

## 3. 描く

1. `references/style.md` を読み、図の種類のスタイルに沿って Mermaid を書く。迷ったら `references/examples/` の見本を見る
2. 保存場所に `.mmd` を書き、描画する:
   ```
   python3 -I ~/.claude/skills/draw-diagram/scripts/render.py ~/dev/diagrams/<テーマ>/<図の名前>.mmd
   ```
   - 同じ名前の `.png` を書き出す。theme（redux-color）と layout（elk）は自動で揃え、`.mmd` にも書き戻す
   - 結果は JSON で出る。`"ok": false` なら `error` に Mermaid のエラーが入っているので、読んで直して描き直す
3. 書き出した PNG を Read で見て、次を確かめる:
   - 結論が一目で読めるか（強調したい違いに目が行くか）
   - 文字が潰れていないか、ラベル同士が重なっていないか
   - 線の交差が多すぎないか。多ければ、要素の書く順番やグループの分け方を変える
   - 色の意味（`references/style.md` の「色の意味」）が守られているか
   - 極端に横長・縦長になっていないか。目安は縦横比 5:1 まで。左から右に 5 段ほど並ぶ構成なら 4:1 前後になるのは避けられないので、それは許容する
4. 問題があれば直して描き直す。3 回直しても良くならないときは、そこで止めて、何が気になっているかをユーザーに伝える
5. 仕上がったら Mac のプレビューで開く:
   ```
   open -a Preview ~/dev/diagrams/<テーマ>/<図の名前>.png
   ```
6. 報告は、保存したパスと、図で何を表したかを 1〜2 行で書く。仮に置いた点があれば、それも並べて確認を取る。Mermaid コードはファイルにあるので、求められない限り全文は貼らない

## 4. 参照・更新・削除

まず保存済みの図を一覧にする（テーマ、図の名前、`%% 目的:` の内容、更新日）。

```
ls -lt ~/dev/diagrams/*/*.mmd
```

- **参照**: 選ばれた図をプレビューで開き、目的と要点を短く説明する
- **更新**: `.mmd` を読み、PNG を見てから直す。何を変えるかが引数で分からなければ聞く。直したら 3 の手順で描き直して上書きする。古い版も残したいと言われたら、別の名前（as-is / to-be など）で新しく保存する
- **削除**: 消す `.mmd` と `.png` のパスを示して、確認を取ってから両方消す。テーマのフォルダが空になったら、それも消す

## 描画の仕組み

- `render.py` は、VS Code に最初から入っている `mermaid-markdown-features` 拡張の描画 JS をローカルの HTTP サーバーで配信し、headless Chrome で描画して切り抜く。通信は自分の Mac の中だけで完結する
- VS Code の Markdown プレビューと同じ描画になるので、`.mmd` を `.md` の ` ```mermaid ` ブロックに貼れば VS Code でも同じ見た目で見られる
- シーケンス図には、登場人物の箱を白に黒枠に、点線の矢印を灰色にする `themeCSS` を自動で足す。構成図の白い箱・灰色の補助線と揃えるため
- VS Code か Google Chrome が見つからないとエラーになる。そのときは、その旨をユーザーに伝える
- mermaid.live、mermaid.ink、kroki など外部の描画サービスは使わない
